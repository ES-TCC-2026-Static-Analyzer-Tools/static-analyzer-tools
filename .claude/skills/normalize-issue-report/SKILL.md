Normalize a raw issues report into flat NDJSON (newline-delimited JSON) records — one
JSON object per line, no enclosing array — so the output can be loaded directly into
BigQuery with `bq load --source_format=NEWLINE_DELIMITED_JSON` and visualized in Looker
Studio.

## Infra Context
- Raw issues reports live in `reports/raw/{pmd,sonar}/`, named
  `<project>_<tool>_issues.json` (e.g. `apollo_pmd_issues.json`).
- Normalized output goes to `reports/normalized/{pmd,sonar}/`, named
  `<project>_<tool>_issues_normalized.ndjson`.
- **Do not hand-transform the JSON.** PMD/Sonar reports can contain thousands of
  violations; rewriting them by reasoning over the text risks truncation and hallucinated
  fields. Always normalize by running the bundled script:
  ```bash
  node .claude/skills/normalize-issue-report/scripts/normalize.js <raw-report-path>
  ```
  The script infers the tool from the parent directory (`pmd`/`sonar`) and the project
  from the file name, so no extra arguments are needed.

## Workflow
1. Resolve the raw report path under `reports/raw/{pmd,sonar}/` from what the user gave
   you (a project name, a file name, or a full path).
2. Run the normalize script on that path.
3. Read the script's stdout. For Sonar, it prints issues read vs. records written —
   treat any mismatch as a bug to investigate, never accept it silently. For PMD, a
   mismatch is *expected* because of the `CyclomaticComplexity` filtering described
   below — the log instead breaks down how many entries were dropped as trivial,
   dropped as class-level, or (only if something is genuinely wrong) left unparsed with
   a `console.warn`. Investigate any unparsed-entry warning; never treat the filtered
   counts themselves as a problem.
4. Report the output `.ndjson` path to the user — for PMD, also mention the companion
   `*_measures_normalized.ndjson` file described below.

## Field Mapping

Every record is flat (no nested objects) and uses snake_case keys so it loads into
BigQuery without renaming: `raw_report`, `sast_tool`, `project`, `normalized_at`, `rule`,
`description`, `file_name`, `line_number`, `severity`, `quality`.

- `raw_report`: exact file name of the raw report (e.g. `apollo_pmd_issues.json`).
- `sast_tool`: `"pmd"` or `"sonar"`.
- `project`: the `<project>` segment of the raw report file name (e.g. `apollo`) — kept
  identical across both tools so PMD and Sonar rows for the same project can be joined in
  Looker Studio. Do not use Sonar's internal `component`/`project` field for this (it's
  spelled differently, e.g. `Apollo-Sonar`).
- `normalized_at`: ISO 8601 UTC timestamp of when normalization ran (BigQuery
  `TIMESTAMP`-compatible).
- `rule`: exact rule identifier from the raw report (PMD `violation.rule`, Sonar
  `issue.rule`).
- `description`: PMD `violation.description`, or Sonar `issue.message`.
- `file_name`: PMD `file.filename` with a leading `./` stripped (PMD emits
  `./src/main/java/...`; Sonar's `path`/`component` never has that prefix — stripping it
  keeps `(project, file_name)` joinable across both tools). For Sonar, `issue.component`
  with the `"<project>:"` prefix stripped; `null` when the issue is project-level
  (component has no `:`, e.g. some architecture/coverage issues).
- `line_number`: PMD `violation.beginline`. For Sonar, `issue.line` when present, else
  `null` (project- or package-level issues have no line).
- `severity`: mapped to Sonar's classic severity scale (`BLOCKER|CRITICAL|MAJOR|MINOR|INFO`)
  for both tools, per the table below. For Sonar this is a direct passthrough of the
  top-level `issue.severity` field — **not** `issue.impacts[].severity`, which uses a
  different scale (`HIGH|MEDIUM|LOW|INFO`).
- `quality`: one of the three Sonar Software Qualities (`MAINTAINABILITY`, `RELIABILITY`,
  `SECURITY`), so PMD and Sonar issues aggregate on the same dimension in the dashboard.

### Severity mapping (PMD `priority` → Sonar severity)

| PMD Priority | Sonar Severity |
| :----------: | :-------------: |
| 1            | BLOCKER          |
| 2            | CRITICAL         |
| 3            | MAJOR            |
| 4            | MINOR            |
| 5            | INFO             |

### Quality mapping

For PMD, match `violation.ruleset` case/space-insensitively (`"Best Practices"` and
`"bestpractices"` are the same key):

| PMD Ruleset     | Quality          |
| :-------------: | :--------------: |
| design          | MAINTAINABILITY  |
| codestyle       | MAINTAINABILITY  |
| bestpractices   | MAINTAINABILITY  |
| errorprone      | RELIABILITY      |
| multithreading  | RELIABILITY      |
| security        | SECURITY         |

For Sonar, prefer `issue.impacts[0].softwareQuality` (already one of
`MAINTAINABILITY|RELIABILITY|SECURITY`). If `impacts` is empty, fall back on `issue.type`:

| Sonar Type      | Quality          |
| :-------------: | :--------------: |
| CODE_SMELL      | MAINTAINABILITY  |
| BUG             | RELIABILITY      |
| VULNERABILITY   | SECURITY         |

### PMD `CyclomaticComplexity` filtering

`rulesets/pmd-ruleset.xml` sets `classReportLevel`/`methodReportLevel` to `1` on purpose,
so PMD emits a `CyclomaticComplexity` violation for **every** method, constructor, class,
enum, interface, annotation and record — that's the only way to get PMD to embed the
actual complexity number in `violation.description` for every unit, not just the ones
that exceed a threshold. Left unfiltered, that would flood the normalized issues table
with thousands of trivial "violations" that Sonar would never report, making PMD and
Sonar issue counts incomparable. The script filters this down to match what Sonar Way
would actually flag:

- **Method/constructor** entries (`"The method/constructor '...' has a cyclomatic
  complexity of N."`) are kept as an issue **only when `N > 10`** — the Sonar Way default
  threshold for `java:S1541` ("Cyclomatic Complexity of methods should not exceed a
  threshold").
- **Class/enum/interface/annotation/record** entries (`"The ... has a total cyclomatic
  complexity of N (highest M)."`) are **never** kept as an issue — modern SonarQube has no
  default active rule for class-level cyclomatic complexity (the old
  `ClassCyclomaticComplexity` rule was deprecated in favor of Cognitive Complexity). The
  `N` ("total") value from these entries is instead summed per file and written to a
  companion measures file — see below.
- Any `CyclomaticComplexity` description that matches neither pattern is kept as an issue
  (old behavior, nothing dropped) and logged with `console.warn` so an unrecognized PMD
  output format is never silently swallowed.

### Derived PMD complexity measures

PMD has no measures API like Sonar's `/metrics/tree` (see the `normalize-measure-report`
skill). Since the class-level `CyclomaticComplexity` entries already give PMD's computed
total complexity per file, the script sums them per `file_name` and writes a second
NDJSON file — `reports/normalized/pmd/<project>_pmd_issues_measures_normalized.ndjson` —
using the *same field shape* as `normalize-measure-report`'s output, so both can land in
one logical BigQuery table. Every field PMD doesn't measure (`loc`, `ncloc`,
`cognitive_complexity`, `sqale_index`, `issues_maintainability`, `issues_reliability`,
`issues_security`) is `null` — not `0` — because PMD genuinely doesn't compute them (`0`
would wrongly imply "measured, and zero").

## Output Format Example

Each line of the `.ndjson` file is one complete, valid JSON object:

```json
{"raw_report":"apollo_pmd_issues.json","sast_tool":"pmd","project":"apollo","normalized_at":"2026-09-13T23:21:54.700Z","rule":"CyclomaticComplexity","description":"The method 'updateCarData(Cars, Cars)' has a cyclomatic complexity of 32.","file_name":"src/main/java/com/onixx/apolloveiculos/api/Services/CarService.java","line_number":264,"severity":"MAJOR","quality":"MAINTAINABILITY"}
{"raw_report":"apollo_sonar_issues.json","sast_tool":"sonar","project":"apollo","normalized_at":"2026-09-13T23:21:54.746Z","rule":"java:S1228","description":"Add a 'package-info.java' file to document the 'com.onixx.apolloveiculos.api.Events' package","file_name":null,"line_number":null,"severity":"MINOR","quality":"MAINTAINABILITY"}
```

The companion PMD measures file (see above) follows the same per-line format used by
`normalize-measure-report`:

```json
{"raw_report":"apollo_pmd_issues.json","sast_tool":"pmd","project":"apollo","normalized_at":"2026-09-13T23:21:54.700Z","file_name":"src/main/java/com/onixx/apolloveiculos/api/ApiApplication.java","loc":null,"ncloc":null,"complexity":1,"cognitive_complexity":null,"sqale_index":null,"issues_maintainability":null,"issues_reliability":null,"issues_security":null}
```

## Loading into BigQuery

Once normalized, load the NDJSON straight in — no flattening step needed. Load the
issues files and the derived PMD measures files into separate tables (different
schemas):

```bash
bq load --source_format=NEWLINE_DELIMITED_JSON \
  dataset.static_analysis_issues \
  reports/normalized/pmd/*_issues_normalized.ndjson reports/normalized/sonar/*_issues_normalized.ndjson

bq load --source_format=NEWLINE_DELIMITED_JSON \
  dataset.file_measures \
  reports/normalized/pmd/*_issues_measures_normalized.ndjson
```
